# Command line

Every `awa` command with its options, generated from the CLI.

```console
awa --help              # the commands, by group
awa run --help          # one command and all its options
awa runs list --help    # one subcommand
```

- A `BLUEPRINT` argument takes the blueprint file or the project folder that contains
  `blueprint.yaml`.
- Every command reads the project `.env`: a value comes from the environment, else from the
  project `.env`, else the default ([Settings](settings.md)). A command that cannot work with the
  configuration it finds stops with one line per problem and exit code 78. The hidden option
  `--skip-preflight` starts without these checks; it prints a warning, and `awa doctor` reports it.
- `--verbose` shows the traceback of an error, before or after the command.
- A command or option whose help starts with `[preview]` has no stability promise yet
  ([Stability](../about/stability.md)).

## `awa`

```text
usage: awa [-h] [--version] [--verbose] [--project DIR] action ...

AI agents for business processes, with hard limits in code, approvals, eval cases and a one-agent
exit to plain LangGraph.

Start:
  ui          [preview] open the web app: set up, add files, describe, connect, test, run
  build       [preview] build a tested project from a description (files: --data)
  init        create a starter project from a template; its tests run offline
  setup       set the model key; optionally database and tracing

Build:
  new         write a blueprint, tool, toolbox, parser, connector or skill from a template
  add         [preview] add a trigger to a blueprint; import tools, graphs and skills
  connect     [preview] set up a project's external systems, setting by setting
  brief       [preview] write a brief for a coding assistant from the project folder
  people      [preview] find colleagues in Entra ID and pin them to roles
  export      eject a one-agent project into plain LangChain and LangGraph code

Check:
  validate    check a blueprint for errors without running it
  show        describe a blueprint's agents, tools, triggers and flow
  eval        run the eval cases and report the pass rate (exit 1 below the target)
  data        [preview] inspect your files, check them against a project, run it on them
  doctor      check the installation, keys and settings, and say what to fix
  check       [preview] check the Microsoft 365 setup with small live reads

Run:
  chat        talk to the system in the terminal; approvals are asked inline
  run         give the system one task and print the answer
  worker      [preview] run the triggers and queued runs until stopped
  serve       [preview] offer the system as a web API with its webhooks and triggers
  mcp         offer the system to MCP clients; pin the tools of its MCP servers

Operate:
  runs        [preview] list, approve, retry, cancel and trace process runs
  trigger     [preview] list a blueprint's triggers or fire one once to try it
  connectors  list, show and test the connectors to your external systems
  skills      list or show the skills
  tools       list the tools of a Python file or the builtins, or call one
  plugins     list, show, check and switch plugins and parts

Settings:
  env         show and change the settings in the project .env (secrets never shown)
  cache       show or clear what the caches hold, or write the project's cache salt
  store       [preview] where runs are kept: status, sqlite or postgres, backup, erase

options:
  -h, --help     show this help message and exit
  --version      show the installed version and exit
  --verbose      show tracebacks for errors (works before or after the command)
  --project DIR  project folder (default: the nearest folder at or above the current one with
                 blueprint.yaml, pyproject.toml [tool.awa] or .awa/)

Three ways to start:
  1. Web app:   awa ui --project invoice-desk
  2. Terminal:  awa build "<your process>" --out invoice-desk [--data <your files>]
  3. Template:  awa init my-desk --template support

Then, in the project folder (a model key is needed: awa setup sets it, awa doctor checks it):
  awa chat blueprint.yaml                    try it
  awa eval blueprint.yaml evals/cases.yaml   test it

Let it run by itself:
  awa add trigger blueprint.yaml             asks what starts it and prints the command:
    awa worker blueprint.yaml                schedule, file drop, email or queue
    awa serve blueprint.yaml                 web requests (webhooks), plus all triggers
  awa runs decide RUN_ID --approve           answer an approval (or Approvals in awa ui)

More: awa <action> --help for every option.
```

### `awa build`

```text
usage: awa build [-h] [--out DIR] [--model MODEL] [--rounds N] [--target RATE]
                 [--guidance GUIDANCE] [--max-requests N] [--max-total-tokens N] [--force]
                 [--no-input] [--data PATH] [--note FILE=TEXT] [--mask {none,placeholders,drop}]
                 [--answer TEXT]
                 process

[preview] Write acceptance tests for the process, design a system against them, evaluate it on
sample data, repair it from the failing cases, and write the project folder. Exit code 1 when the
target pass rate is not reached.

positional arguments:
  process               plain-language description of the process

options:
  -h, --help            show this help message and exit
  --out DIR             project folder (default: ./<system name>)
  --model MODEL         model profile or provider:model for every step
  --rounds N            evaluation rounds (default 3)
  --target RATE         pass rate to stop at (default 1.0)
  --guidance GUIDANCE   extra requirements for the design
  --max-requests N      model-call limit for the whole build
  --max-total-tokens N  token limit for the whole build
  --force               overwrite an existing project
  --no-input            never ask (for example what should start it, or the questions about your
                        files: they are printed as JSON and the exit code is 2)
  --data PATH           build on your real files: a file, folder or glob, repeatable. They are
                        copied into the project's data/ folder (the originals are never touched)
                        and replace invented sample data
  --note FILE=TEXT      what must happen with a file of --data (a name or glob), repeatable
  --mask {none,placeholders,drop}
                        what the design model sees of personal data in the summary of your files:
                        everything (none, the default), placeholders such as <IBAN_1> for names,
                        tax and bank numbers, email addresses and phone numbers, or no sample
                        values (drop). Agents that read your files through the file tools see the
                        file content unmasked at run time: give an agent only the files it needs
  --answer TEXT         your answer to the questions of an earlier build of the same description
                        and files (q1=TEXT answers one question), repeatable
```
